# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`data-manager` is a Flask app replacing the sibling `data-pipeline` scripts (OSM → border → valhalla → pelias, plus tiles) with orchestrated, DB-tracked stages. `DESIGN.md` is the authoritative plan (architecture, full schema, phased roadmap, open risks) — read it before adding features. Phases 0–6 are built (foundations, configuration UI, downloads and the OSM/border/Valhalla/styles/Pelias stages); assembly/publish/deploy (Phase 3) is not (`DESIGN.md` "Modular Development Plan" has the status per phase). Design decisions worth remembering: clean slate (no import of legacy pipeline output), config authored via a map UI (Phase 1) rather than YAML, and `data-pipeline` must stay untouched (code-wise; it is only bannered as deprecated). The platform-level migration plan — steps across services, infra and the copy-based deployment strategy (per-artifact roots, `current` symlink, copy → verify → activate → rollback) — is in `../Docs/MIGRATION-DATA-MANAGER.md`; keep it in sync with `SERVICES.md` and `DESIGN.md`.

## Workflow

- **Branch, signed commits, pull request.** Every change to data-manager goes through a topic branch and a pull request, never straight on `main`. CI runs the shared DCO check (`.github/workflows/ci.yml`), so commits carry a `Signed-off-by` trailer: `git commit -s`. Use separate commits per logical part and a PR description that says what was verified (tests, real runs) and what was not.
- **Sibling repos are read-only here.** `../tilesservice`, `../swayrider-api`, `../infra` and `../data-pipeline` are read for analysis only; their code is changed on the developers' machines. Anything those changes need (paths, commit hashes examined, exact changes, tests, contracts, fixtures) is written down in data-manager's documents so the work can continue elsewhere: `SERVICES.md` (the contract per service), `TILESSERVICE-PMTILES.md` (analysis and handover for `tilesservice` and `swayrider-api`), `DESIGN.md` (decisions).
- Restart `./debug.sh` (worker included) after every change to stage code; the worker does not reload.

## Commands

Uses a local `.venv` (pip + pinned `requirements.txt`); copy `.env.example` to `.env` for local overrides.

```
pytest                                   # all tests (pytest.ini: testpaths=tests, pythonpath=.)
pytest tests/test_stage_contract.py::test_name   # single test
alembic upgrade head                     # migrate (script_location=migrations)
flask run                                # needs FLASK_APP=wsgi.py (set in .env.example)
flask seed-countries                     # idempotent country catalog seed
flask autofill-countries                 # fill unset Geofabrik paths / OpenAddresses sources from provider indexes (verified live)
flask export-countries                   # write countries.md review sheet
flask evaluate-overlap [--all]           # recompute stored region overlap
python run_worker.py                     # RQ worker on queue "data-manager"
./debug.sh                               # dev server on :5050 + a worker (stopped on exit; NO_WORKER=1 to skip)
```

The worker and any RQ-based tests need the dedicated Redis (`REDIS_URL`, default `redis://localhost:36389/0`) from `infra/data-manager/compose.yaml` in the separate `infra` repo — not the shared `sw-dev-redis` on 36379.

## Architecture

- **Flask never runs domain logic.** It reads/writes SQLite and enqueues RQ jobs; long-running stage work runs in the RQ worker (`datamanager/jobs/`). Job bodies in `jobs/tasks.py` are plain functions so tests can compare in-process vs. RQ-executed results.
- **Blueprints**: one subpackage per UI section under `datamanager/blueprints/<name>/` (`routes.py`, its own `templates/<name>/` and `static/`), exporting `bp` and an optional `NAV` (`NavItem`) that drives the sidebar. Register new sections in `blueprints/__init__.py`. Shared shell lives in `datamanager/templates/base.html` + `static/css/app.css`; query logic in `datamanager/services/`. Pages are server-rendered with htmx partial swaps (full page when no `HX-Request`).
- **Plain SQLAlchemy, not Flask-SQLAlchemy**, because the worker needs sessions with no app context. `datamanager/db.py` is the single engine/session factory shared by Flask, worker, and Alembic's `migrations/env.py` (WAL + foreign_keys pragmas set via a connect hook), so all three always hit the same DB file. Alembic uses `render_as_batch=True` for SQLite `ALTER TABLE` limits. Models live in the `datamanager/models/` package; each phase migrates only the tables it needs.
- **Config split**: `datamanager/config.py` (`AppConfig`, env/.env-driven) is *bootstrap only* (DB path, Redis, data root). Domain config (regions, profiles) will be DB-driven from Phase 1 — don't put it in env/YAML. Tests override `DATA_ROOT`/`DATABASE_PATH` via the `tmp_data_root` fixture in `tests/conftest.py` (which also provides `db_session`, `app`, `client`).
- **Stage contract** (`stages/contract.py`, `stages/registry.py`): each stage is a `StageRunner` declaring `produces`/`consumes` asset types; `StageRegistry.resolve_order` topologically sorts and transitively pulls in producer stages (raising `UnresolvedDependencyError` / `CyclicDependencyError` from `errors.py`). Ordering is structural, not by comment. `NoOpStage` is the synthetic stage exercising this.
- **Country catalog** (`countries/`): auto-derived from Natural Earth admin-0 geometry (`natural_earth.py` downloads/caches the zip, writes per-country GeoJSON under `data/library/country-geometry/`) merged with hand-curated `countries/curated/countries.yml` (geofabrik path, WOF code, OpenAddresses files) by `seed.py`. **All** Natural Earth countries are seeded; only curated ones have a `geofabrik_path` (`Country.is_curated`) and are buildable — the rest are display-only. Locality-boundary sources (`country_boundary_source`, registry `datamanager/boundary_sources/`: OSM admin levels, official polygons, GeoNames postal) follow the same pattern via the generic `services/country_sources.py` and are consumed only by the future Pelias stage (see DESIGN.md "Locality boundaries"). Address sources are per-country rows (`country_address_source`) backed by the registry in `datamanager/address_sources/` (OpenAddresses, Overture; OSM comes from the Geofabrik extract) — add a source by implementing `AddressSource` there plus a modal partial. Migrations run with `foreign_keys=OFF` (see `migrations/env.py`) because SQLite batch mode recreates tables and would cascade-delete child rows. The DB is the source of truth for curated fields: re-seeding only fills in still-unconfigured countries and never overwrites UI edits (right-click a country on the map → details/edit modal, handled by the `countries` blueprint, which also verifies the Geofabrik URL). Regions (`services/regions.py`, models `Region`/`RegionCountry`) are managed on the Configure → Map tab (list panel + right-click menu in `configure/static/map.js`): add to / remove from the *active* region only, one region per country per configuration. Overlap (100 km around the core) and border pairs (10 km buffers, true distances via a local azimuthal equidistant projection, not the legacy 3857) are derived in `services/overlap.py` with the resulting overlap stored in `region_overlap` (auto rows recomputed by `regions.evaluate_overlap` on every core change; include/exclude rows are user overrides; `flask evaluate-overlap`). The Configure → Resolved tab (`services/resolve.py`) derives the per-region lists stages consume (core/overlap Geofabrik paths, WOF codes, OpenAddresses files with per-region exclusions in `region_openaddresses_exclusion`, SRTM boxes incl. overlap, warnings, hash) and exports them in the legacy `config-mini.yml` shape. Countries can be carved per configuration (right-click → Carve out…, draw the part to keep; `services/carve.py`, table `country_carve`): every derived geometry (overlap, border pairs, buffer) uses the country clipped to that polygon, via the optional 4th element of `overlap.geometry_key`. (The former Configure → Tiles tab — extent, tile grid, Geofabrik tile regions, tables `tile_settings`/`tile_override`/`tile_source_override` — was removed 2026-10-01 together with `services/tiles.py`: tiles are downloaded as a planet build, nothing is derived per configuration.) The map endpoint (`/countries/api/geojson`) serves simplified, cached geometry (full detail stays on disk).
- **Global settings and tools** (`services/settings.py`, table `global_setting`, Settings section): registry-in-code with defaults, DB holds only overrides; `datamanager/tools.py` + `services/tools.py` detect the required external tools (cached, re-detect buttons, custom path, Debian install hints). Stages must check their tools before running.
- **GTFS feeds** (`services/regions.add_gtfs_feed`, table `region_gtfs_feed`, Configure → Transit tab): per-region feed URLs, part of the resolved config/hash and the legacy `gtfs_feeds` export; consumed by the future Pelias stage.
- **Runs and downloads** (Phase 2 in progress; `services/runs.py`, `services/downloads.py`, `stages/`, Build section): a stage run is a `build_run` (+ `build_step` rows fed by the runner's `step_cb`/`progress_cb`) executed by the generic job `jobs/tasks.run_stage`; stages are registered in `stages/builtin.py`. A clean run ends `awaiting_review` with a validation `report_json`; **only approved runs feed later stages** (manual gate, Approve/Reject on the run page). Downloads are versioned: every fetch that brings new data is an immutable `download_record` (`source_key` like `osm:europe/belgium` + UTC `version_label`), identical bytes share one file, upstream-unchanged (ETag/Last-Modified) makes no new version. `downloads.resolve_version` picks the run's override, else the pinned version, else the newest approved one. Cleanup keeps the newest N (default 2), pinned and in-use versions, dry-run first (Build → Downloads, grouped per source kind in expandable sections with one table each). Files a stage produces are `asset` rows (`services/assets.py`, stored under `library/assets/<kind>/<run_id>/`, `produced` until the run is approved, `assets.current` = newest approved per configuration/type/name). Implemented stages: `download-planet` (versioned `planet:osm`, at most 2 kept, `use_existing`/`local_file` for testing), `extract-countries` (planet → per-country `country-pbf` assets via Geofabrik `.poly` files, one `osmium extract -c` pass, skipped per country when planet version + polygon hash are unchanged), `download-tiles` (newest daily Protomaps planet build, `tiles:planet`, ~140 GB, listed by `build-metadata.protomaps.dev/builds.json`, PMTiles header/layers validated by `services/pmtiles.py`, `download.tiles_keep` = 1; no configuration needed), `download-osm` (Geofabrik alternative, `osm.source=geofabrik`), `download-srtm` (`stages/download_srtm.py`: 1° Skadi elevation tiles of the regions' SRTM boxes, versioned per tile `srtm:N50E004`, unpacked for Valhalla into `library/srtm/<run_id>/`), `border` (`stages/border.py` + `services/borders.py`: region outlines and per-pair road-crossing CSVs from the approved region PBFs and border polygons, via osmium tags-filter/export + shapely, skipped when inputs are unchanged; the run page has a Leaflet review map from `report_json.map`), `valhalla` (`stages/valhalla.py` + `services/valhalla_data.py`: per region `tiles.tar`/`admin.sqlite`/`tz_world.sqlite`/edge polylines assets from the approved full PBF and approved SRTM run; needs Valhalla compiled via the Build button in Settings → Tools, `services/valhalla_build.py`, a tool cache under `data/tools/valhalla`, not an asset), `styles` (`stages/styles.py`: `style-light.json`/`style-dark.json` assets per configuration from the Style tab), `polygons` and `osm-extract` (`stages/osm_extract.py` + `services/osmium.py`: per region core and full `.osm.pbf` from the approved country PBFs and approved polygons, carve-aware, per-region runs via `params.regions`), of which `polygons` (`services/polygons.py`: per region core, 100 km overlap and per bordering pair 10 km border `.poly`/`.geojson`, plus carve keep-polygons; full-detail geometry, true-distance buffers, review map on the run page). `download_source` is not a table (sources are derived from the resolved config). The Build page shows a colored indicator per stage (`stages/status.py`: running / awaiting review / failed / blocked / not run yet / up to date / outdated); "outdated" compares a fingerprint stored in the meta of the assets a stage produced (`polygons_fingerprint`, `region_fingerprint`, the planet record id on country PBFs) with the current inputs.
- **Pelias (Phase 6)**: per region, built from approved inputs; the importers are cloned and built by the tool `pelias_build` (Settings → Tools, `services/pelias_build.py`, machine-local under `DATA_ROOT/tools/pelias`). `download-pelias-data` (`services/pelias_sources.py`: WOF admin/postal bundles, GeoNames per country `geonames:<cc>`, OpenAddresses, placeholder; fingerprinted per source), `wof-patch` (`services/wof_patch.py`: patched WOF locality database per country, replaces the plain bundle when approved), `download-overture-gtfs` (`services/overture.py`: `overture:<slug>-places|addresses` CSVs for the csv-importer from `overturemaps` with the approved overlap polygon's bbox, `gtfs:<slug>-<feed id>` zips; failures are warnings), `pelias` (`stages/pelias.py` + `services/pelias_es.py`/`pelias_data.py`: one temporary Elasticsearch docker container per region with bind-mounted directories that are always removed, importers in the order `schema`, `whosonfirst`, `geonames`, `openaddresses`, `openstreetmap`, `polylines`, `csv-importer`, `transit` (the last two optional: a failure or 0 documents is a warning), assets `pelias-index-snapshot`/`pelias-config`/`pelias-wof`; `PLAN_VERSION` is part of the fingerprint, bump it when the imported data changes) and `pelias-interpolation` (`services/pelias_interpolation.py`: `street.db`/`address.db` from the node entry points of the `interpolation` repo, stall watchdog). A stage's `report_json` must carry `record_ids` for every download it fetched, otherwise approving the run does not approve them (`downloads.apply_review`). Importers can exit 0 after rejecting their config: judge them by documents added, not by exit code. Deploy side (snapshot restore, alias switch, PIP/interpolation services) is not built; see DESIGN.md "Pelias stage".
- **Tile schema**: tiles are not built but downloaded (`download-tiles`, Protomaps basemap schema, Z0–15; decision 2026-10-01 in DESIGN.md → "Tiles stage: Protomaps PMTiles extract"; changes needed in tilesservice/clients in `SERVICES.md`). **Decision 2026-10-05:** the whole planet is the tileset (no extent extract), `tilesservice` serves tiles and styles from the release directory (manifest, several named styles each a light/dark pair, public URLs substituted when served, self-hosted glyphs/sprites; contract in `SERVICES.md`); the `styles` stage still produces one pair and has to grow to that. The map styles (light/dark, label zoom config, `services/map_styles.py`) are the vendored `@protomaps/basemaps` flavors in `datamanager/styles/protomaps-*.json` (regenerate with `styles/generate.mjs`); the `places_locality` layer is split per label kind at load time so each kind gets its own minimum zoom. The Style tab previews them over the approved `tiles:planet` file, served by `/configure/style/tiles.pmtiles` (Range) and read with the pmtiles protocol; glyphs/sprites of the preview are vendored in `blueprints/configure/static/map-assets/` (`styles/fetch-assets.sh`), exported styles use Settings → Public URLs (default `protomaps.github.io/basemaps-assets`).
- **Publish/deploy (not built)**: package (tagged archive in `releases/<tag>/`) + deploy configuration (pluggable driver, first `compose-single-machine`) = deploy; spec in `RELEASE-CONTRACT.md`. Code changes for it are made on the data-manager server, not on the dev machine.
- **Runtime data root** (`DATA_ROOT`, gitignored `data/`): `state/db.sqlite3`, `downloads/`, `library/`, `work/<run_id>/`, `releases/`, `deploy-state/`.
